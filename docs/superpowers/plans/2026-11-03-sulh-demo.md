# Sulh database demo implementation plan

Goal: Complete a persisted demo booking journey ending in skippable payment.
Architecture: Existing Flutter client calls authenticated Edge API; service-role-only SQL functions atomically seed and transition flagged demo rows.
Stack: Flutter/Dart, Supabase/Postgres, Deno/TypeScript.
Spec: docs/superpowers/specs/2026-11-03-sulh-demo.md

## Constraints
Keep application IDs and existing financial statuses. No real payments or email from simulation. Only booking customer may simulate their own server-flagged demo booking.

## Review focus
Retries must not duplicate catalog or advance twice; cancelled bookings must not advance; ownership must be checked server-side; skip must never set Paid; leaving/reopening must preserve state.

## Tasks
1. Database catalog, atomic transitions and Arabic search. Tests: SQL rollback assertions for repeat generation, all transitions, ownership, real bookings, cancellation and skip idempotency. Interface: seed_sulh_demo_catalog() and advance_sulh_demo_booking(uuid,bigint,text,boolean).
2. Authenticated API integration and demo state serialization. No notification-email sending from demo endpoints. Interface: POST /api/Demo/catalog; GET /api/Demo/bookings/:id; POST /api/Demo/bookings/:id/advance with expectedStatus and skipPayment.
3. Flutter service and journey screen, catalog generation button, booking autofill, resume from appointments, localization and platform display name. Tests: mocked HTTP errors, widget flow to checkout/skip/resume; regression suite.
4. Run local Node/SQL checks; use branch CI for Flutter when SDK unavailable. Review diff and deliver a PR with actual verification and deployment status.

Execution: native within isolated checkout and feature branch. User request authorizes development; no additional design permission gate. Deployment decision follows concrete verification.
